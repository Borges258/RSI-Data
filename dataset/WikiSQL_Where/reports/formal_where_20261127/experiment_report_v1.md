# 先验知识与原子技能流对 WikiSQL WHERE 条件生成的联合作用：一项 2×2 消融实验

**实验编号**：`formal_where_20261127`  
**报告版本**：第一版（已完成实验部分；两项验证实验进行中，见 5.9）  
**模型**：`gpt-5.6-sol`  
**评价队列**：410 条经审计的 Gold 样本（405 条 Gold WHERE 非空，5 条为空）  
**报告性质**：描述性实证报告，不做显著性推断

---

## 摘要

本文报告一项在 WikiSQL WHERE 条件生成任务上的 2×2 因子消融实验，考察两个因素及其交互作用：**(i) 是否注入画布式先验知识（Canvas Prior Knowledge）**；**(ii) 是否使用原子技能流（Atomic WHERE Skill Flow）**。四组分别为 E0（两者均无，复用冻结的 E4 预测）、E1（仅先验知识）、E2（仅原子技能流）、E3（两者结合）。

在端到端口径（分母 410）下，E3 取得最高的归一化结构匹配（82.20%）与非空 WHERE 行一致率（82.96%），相对 E0 分别提升 26.59 与 24.19 个百分点。E1 以最低成本（每样本 1 次调用、约 1.04 万输入 Token）达到 78.29% 的归一化匹配与 83.66% 的 WHERE 行一致率。E2 在已完成样本内的结构精度与 E3 接近，但因 37 条 grounding 失败，安全完成率降至 89.76%。因子分解显示两类干预的收益高度重叠：知识的效应在无技能时为 +22.68 pp，在有技能时缩小为 +5.12 pp；交互项约为 −17.56 pp，呈明显次可加。

对第一版 14 类错误模式的分层分析进一步表明，干预主要修复“值不在表内”（W02，0.0%→98.9%）与“遗漏条件”（W09，22.2%→100.0%），而列映射类（W04/W05/W08）仍是主要残差。

**关键词**：WikiSQL；WHERE 条件生成；先验知识；原子技能流；2×2 因子设计；消融实验

## 1. 引言与研究问题

结构化查询生成中的 WHERE 子句要求模型同时完成三件事：识别过滤列、选择比较算子、生成可被数据库执行的条件值。仅依赖端到端提示时，模型容易在列名歧义、值未落地（hallucinated value）与多条件组合上出错。本文分别考察两类干预：

- **先验知识（Prior Knowledge）**：以画布（Canvas）视图为来源，经编译得到的表级知识图，包括全局语法原子、表字段原子、条件模式、决策规则与关系边，作为稳定的结构化上下文注入模型。
- **原子技能流（Atomic Skill Flow）**：将 WHERE 生成拆分为可校验的技能节点（条件抽取 → 多条件抽取 → 条件校验/值落地 → 条件装配），由流程引擎编排多个模型调用，并在无法确定时返回澄清（CLARIFY）。

据此提出三个研究问题：

- **RQ1（知识主效应）**：注入先验知识能否提升 WHERE 结构与执行一致性？
- **RQ2（技能主效应）**：使用原子技能流能否提升 WHERE 结构与执行一致性？
- **RQ3（交互效应）**：两类干预同时启用时，收益是叠加、互补还是重叠？

## 3. 实验原理

### 3.1 任务形式与可执行约束

给定问句 \(q\) 与表 \(T\)（表头、列类型、行数据），系统输出 WHERE 条件列表：

\[
C = [(c_1, o_1, v_1), \ldots, (c_k, o_k, v_k)]
\]

其中 \(c_i\) 为列索引，\(o_i \in \{=, >, <\}\)（编码 0/1/2），\(v_i\) 为条件值。可执行性要求：列索引合法、算子属于 0/1/2、条件值能在目标列原文中落地（grounding）。评价时把 \(C\) 与 Gold 条件分别在 SQLite 上执行，比较筛选出的行集合；`sel` 与 `agg` 不参与生成，仅用于保持表与问句的原始语义。

### 3.2 先验知识：从画布视图到可注入的知识图

**来源与编译。** 先验知识并非手工拼接的提示模板，而是从既有画布视图编译得到：

1. 以 `wikisql_where_knowledge.tsx` 的画布组件为唯一来源，调用 `createWikiSqlWhereKnowledgeView` 生成表级视图；
2. 调用 `extractWikiSqlWhereKnowledge(view, tableId)` 抽取为知识图；
3. 每张表编译一次，结果写入 `knowledge_cache.json`，并将缓存哈希写入运行清单，样本间与断点续跑时复用，避免重复构建引入噪声。

知识图包含四个层次与一组关系边（表 5）。

**表 5 先验知识的组成**

| 层次 | 标识 | 作用 | 典型内容 |
| --- | --- | --- | --- |
| 全局语法原子 | `g-*` | 规定问句表达与算子/值的映射 | `g-eq`（等值→0）、`g-gt`（more than→严格大于）、`g-lt`、`g-inclusive`（at least/at most 的边界语义）、`g-literal`（文本取原文）、`g-threshold`、`g-and`、`g-or`、`g-column`、`g-count`、`g-ambiguous` |
| 表字段原子 | `t-<table>-field-N` | 描述当前表每一列的类型与取值证据 | `kind=COLUMN`、`source=CURRENT_SCHEMA`、`trust=CURRENT_TABLE_FACT`，`structured` 中记录类型与取值样例 |
| 条件模式 | `p-*` | 约束可生成的条件形态 | `p-text`、`p-number`、`p-multi`、`p-unsupported` |
| 决策规则 | `d-*` | 规定模式选择与消歧策略 | `d-implicit-eq`、`d-explicit-eq`、`d-gt`、`d-lt-and-gt`、`d-with-two`、`d-literal-form` |
| 关系边 | `where-rel-*` | 连接语法、字段与模式，形成可检索的约束网络 | 例：`g-column --CONSTRAINS--> p-text`，说明“等值条件必须先确认过滤字段” |

每个知识原子均带有 `id / title / kind / source / scope / trust / support / statement / cues / structured` 等字段。例如全局原子 `g-eq` 的 `statement` 明确写出“明确的属性等值表达可映射到 WikiSQL 运算符 0；不得只凭介词猜测字段”；表字段原子则以 `CURRENT_SCHEMA` 为来源、以 `CURRENT_TABLE_FACT` 为信任级别，限定“只在当前表内有效”。这种“规则 + 证据 + 作用域”的三元结构，使知识既可被模型阅读，也可被流程节点按 ID 检索与校验。

**注入方式。** 三类在线路径都遵循同一原则：先放置稳定的 `question + table + knowledge` 前缀，再追加阶段数据；因此同一问句的重复前缀可被供应商缓存。E1 的响应直接返回 `knowledgeIds`（如 `g-eq`、`t-<table>-field-N`、`d-explicit-eq`、`p-text`）、`promptSha256` 与 `usage`，可据此核对知识是否实际进入提示；E3 的 Flow 请求体则显式携带 `structure` 与 `knowledge`。E2 为隔离技能流效应，传入同版本、同表 ID、但 `atoms/patterns/relations` 均为空的 `knowledgeContext`。

### 3.3 原子技能流：技能节点如何编排并参与模型调用

**编排单位。** 原子技能流是一个由 FlowEngine 执行的技能图（Flow ID 固定，定义文件哈希写入运行清单）。运行器只发送一次请求，把问句、表以及（可选的）先验放进 `params.request`；后续的节点调度、状态传递与模型调用全部由 FlowEngine 完成，运行器不参与编排。

**阶段与职责。** 从 Flow 的状态与失败映射可以观察到四个阶段（表 6）。响应中的终止阶段为 `WHERE_CONDITION_ASSEMBLE`，中间失败会映射到 `EXTRACT`、`MULTI_EXTRACT` 或 `VALIDATE`。

**表 6 原子技能流的阶段**

| 阶段 | 职责 | 关键输出 | 失败映射 |
| --- | --- | --- | --- |
| `WHERE_CONDITION_EXTRACT` | 从句切分，抽取候选条件及其问句跨度 | `surface`、`value`、`start/end`、`clause` | `FLOW_ERROR`（EXTRACT） |
| `WHERE_MULTI_CONDITION_EXTRACT` | 处理并列、多条件与需要澄清的结构 | 合并后的条件集合 | `CLARIFY`（MULTI_EXTRACT） |
| `WHERE_CONDITION_VALIDATE` | 列候选与算子选择，强制值在目标列落地 | `columnIndex`、`columnCandidates`、`columnMatchReason`、`operator`、`grounded`、`groundingStatus` | `GROUNDING_FAILED`（VALIDATE） |
| `WHERE_CONDITION_ASSEMBLE` | 汇总校验通过的条件并编码为 `conds` | 最终 `conds`、`warnings` | 终止阶段 |

**模型如何参与。** 每个技能节点按需调用模型，并以结构化 JSON 传递状态；E2/E3 平均每样本约 4.0 次成功模型返回，与“抽取—多条件抽取—校验—装配”的多节点编排相符。响应保留了每个条件的可核验证据：问句子串（`surface` 与 `clause`）、列候选及匹配理由（`columnMatchReason`）、落地状态（如 `EXACT_MATCH`）。因此，技能流的产出不是一段自由文本，而是“条件 + 证据 + 状态”的结构化记录。

**失败语义。** 任一阶段失败都会转为显式状态（`FLOW_ERROR`、`CLARIFY`、`GROUNDING_FAILED`），而不是静默给出错误条件。这使 SCR 在 E2/E3 上低于 E0：E0 的失败只体现为条件校验不过，而 E2/E3 把不可落地、需澄清与流程错误分别记录。该差异是“覆盖率—精度”权衡的直接来源。

### 3.4 因子隔离与机制假设

E1 与 E2 分别隔离“知识”和“技能”两个因子；E3 同时启用。知识以稳定前缀注入，技能以多节点校验编排；两者都可能修复“列歧义”与“值未落地”，因此存在收益重叠的可能。

- **知识假设**：先验知识主要降低列歧义与值未落地，应同时提升结构匹配与执行一致率，并减少 grounding 失败。
- **技能假设**：阶段化校验主要拦截非法算子与不可落地值，应提升执行一致率，但可能因更严格的门槛降低安全完成率。
- **交互假设**：若两类干预修复同一批错误，联合收益应低于两者单独收益之和（次可加）。

## 6. 讨论

### 6.1 主效应

- **先验知识（RQ1）**：在无技能流时，E1 相对 E0 在归一化结构（+22.68 pp）与 WHERE 行一致（+24.39 pp）上均有大幅提升，且执行一致增益高于结构增益，说明知识主要改善“值能否落地/列是否选对”，而非仅对齐表面形式。
- **原子技能流（RQ2）**：E2 相对 E0 亦显著提升（+21.46 pp / +18.54 pp），但代价是安全完成率下降 9.27 pp，主要来自 37 条 grounding 失败。技能流的价值更多体现为“把错误变成可观测失败”，而非直接提高覆盖率。

### 6.2 交互效应（RQ3）

以归一化结构匹配衡量，知识在“无技能”下的效应为 +22.68 pp，在“有技能”下缩小为 +5.12 pp；技能在“无知识”下为 +21.46 pp，在“有知识”下缩小为 +3.90 pp。交互项为 −17.56 pp，呈明显次可加。合理解释是两类干预修复的失败集合高度重叠：都集中在列歧义与值落地两类错误上，因此联合使用难以获得叠加收益。

执行一致口径下，E3 与 E1 的差异为 −0.49 pp（配对 7 增 / 9 失），提示在知识已充分的条件下，技能流并未带来稳定的行级收益；其收益主要体现在结构归一化（+3.90 pp）与 grounding 失败减少（37 → 15），但后者对最终行一致的正向作用被其他回退抵消。

与结构/执行口径不同，SCR 的交互项为 +9.02 pp：知识在有技能时把 SCR 从 89.76% 拉回 95.37%，说明知识不仅提升精度，也补偿了技能流因严格 grounding 造成的覆盖损失。

### 6.3 覆盖—精度权衡

E2 的条件归一化精度（85.87%）高于 E1（81.89%），但端到端归一化（77.07%）低于 E1（78.29%）。这意味着技能流在“能完成的样本”上略优，却因更严格的门槛损失了更多样本。若应用场景更看重“少出错”，E2/E3 的显式失败更可取；若更看重“尽量给出答案”，E1 的覆盖—精度折中更优。

### 6.4 成本效益

按端到端归一化正确数计算，E1 每百万输入 Token 约产生 75 条正确样本，E2 约 36 条，E3 约 19 条。E1 的成本优势来自单次调用与较短提示；E3 的高成本主要来自知识上下文重复注入，而非调用次数。若知识可跨样本缓存或压缩，E3 的成本曲线仍有下降空间。

### 6.5 分层证据的含义

14 类分层表明，两类干预的收益集中在“值级”错误：W02 与 W09 在 E1/E3 下被大幅修复；而列映射（W04/W05）、方向反转（W08）与多出条件（W06）几乎没有被覆盖。这与总体交互效应一致：知识和技能都在解决“值能否落地”，因此彼此重叠；真正的残差位于“列语义与条件结构”，需要新的干预，而不是继续堆叠同类上下文或校验。

### 6.6 失败归因

四组未安全完成样本与第二轮 Gold 审计标记存在部分重叠：E0 的 4 条未完成中有 2 条（`test:908:1-14035132-3`、`test:3389:1-25696729-8`）对应审计中判定为列映射错误或不可表达的 Gold；E1/E2/E3 的失败集合中也分别有 4/6/5 条落在 36 条标记样本内。这说明一部分残差来自数据与 Gold 本身，而非生成能力；同时也意味着各臂的绝对分数存在共同上限。

## 7. 有效性威胁

1. **选择效应**：596 条原始子集全部是 E4 未执行正确的样本，410 条有效队列因此是“失败富集”的困难集合。E0 的 55.61% 等绝对数值不能外推为官方 WikiSQL 测试性能，也不能与文献中的官方 EX 直接比较。
2. **基线非同路径**：E0 复用历史 E4 的完整 SQL 预测，其推理路径、提示与校验证据均与 E1–E3 不同；E0 的高 SCR（99.02%）部分来自更宽松的历史校验口径，不能与在线臂的 SCR 直接等价比较。
3. **知识因子的接口不对称**：E1 只接收 `knowledge`，E3 接收 `structure + knowledge`；因此“知识”在两个技能水平上的操作化并不完全一致，交互项可能部分反映接口差异。本文在表 3 明确记录该差异，但无法在不改动服务接口的前提下消除。
4. **任务范围限制**：E1–E3 只预测 WHERE `conds`，不预测 `sel`/`agg`，因此无法计算与 E0 可比的官方全 SQL 执行准确率（EX）；本文以 WHERE 行一致作为替代指标，二者不可互换。
5. **Gold 修订与共同上限**：Gold 经人工审计修订，36 条标记样本仍保留在分母中；历史 E4 的官方得分不能直接转抄为本 410 条上的结果。
6. **分层标签口径**：14 类标签在 410 条上复算，与审计清单存在 少量边界样本的归属差异；分层结果用于解释错误结构，不改变主表口径。
7. **统计效力**：单模型、单次运行、无重复采样与置信区间，配对变化与交互项均为描述性统计；不应据此宣称因果收益或显著性。
8. **空结果样本**：5 条 Gold 为空的样本单独计入“双方空结果”，未混入非空执行一致率，避免虚高。
9. **成本口径**：缓存输入 Token 已包含在输入 Token 内，不可相加；调用次数仅统计可恢复的成功模型返回，供应商已接收但请求失败的调用可能未计入。

## 8. 结论

在固定 410 条审计后 WikiSQL WHERE 样本上，先验知识与原子技能流都能显著改善条件生成质量：

- 单独使用先验知识（E1）即可将归一化结构匹配从 55.61% 提升至 78.29%，WHERE 行一致从 59.27% 提升至 83.66%，且成本最低；
- 单独使用技能流（E2）带来相近的结构收益，但 grounding 失败导致覆盖下降，端到端执行一致低于 E1；
- 两者结合（E3）取得最高的归一化匹配（82.20%）与非空执行一致（82.96%），但相对单因素增益呈明显次可加（交互约 −17.56 pp），且输入成本约为 E2 的 2 倍。

分层结果进一步表明，现有收益主要来自“值落地/条件补全”，列映射与条件结构类错误仍是残差。更实用的配置取决于目标：追求低成本高覆盖时优先 E1；追求最高结构质量且可接受更高成本时选择 E3；若需要显式失败与可归因性，E2/E3 的阶段化状态更利于线上治理。

原能力回归与 400 条金标 2×2 复核仍在进行中（5.9），其结果将用于检验上述效应是否稳定；在结果回收前，本文不对其作任何推断。

- **归一化结构匹配**：将条件值做 Unicode `casefold`，把 AND 条件视为保留重复项的多重集进行比较；因此条件顺序不同但集合一致时仍判为匹配。

- **SCR**：成功返回 + 合法条件三元组（列索引在表内、算子属于 `{=, >, <}`、值可落地）；E2/E3 额外要求 Flow 完成且 `WHERE_CONDITION_VALIDATE.valid=true`。
