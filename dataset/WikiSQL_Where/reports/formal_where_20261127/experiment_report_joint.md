# 先验知识与原子技能对 WikiSQL WHERE 生成的影响：失败集消融与原能力回归

**研究类型**：单模型、固定队列、描述性实验  
**模型**：`gpt-5.6-sol`  
**实验编号**：`formal_where_20261127`；`retention_return_20261127`  
**报告版本**：合并版，2026-11-27（运行记录时区 UTC+08）

## 摘要

本文研究结构化先验知识与十个 WHERE 原子 Skill 对 WikiSQL 条件生成的作用。主实验在 410 条经 Gold 审计的 E4 失败样本上进行 2×2 消融：E0 复用冻结的 E4 预测，E1 仅用画布先验知识，E2 仅用 Skill Flow，E3 同时使用二者。另在 400 条从 E4 执行正确样本中按 Gold 条件数分层抽取的回归集上运行 E1–E3，以检验原有能力的保留情况。两组使用相同的 WHERE 评估器和安全完成率（SCR）定义，并保存逐样本结果及模型返回证据。

主实验中，E3 的归一化结构匹配为 **337/410（82.20%）**，高于 E1 的 321/410 和 E2 的 316/410；E1 的 WHERE 行一致为 **343/410（83.66%）**，略高于 E3 的 341/410。回归集中，E3 的归一化结构匹配为 **386/400（96.50%）**，WHERE 行一致为 **388/400（97.00%）**；冻结 E4 在同一 WHERE 口径下为 399/400，说明仍有 11 条行级回退。两组结果共同显示：联合方案在结构匹配上有增益，但增加输入 Token，且不能保证保留所有既有成功案例。十四类初始失败模式的分层表明，值落地和条件遗漏的改善较大，列映射、比较方向和多余条件仍是主要残差。本文仅报告 WHERE 级指标，不把 WHERE 行一致称为完整 SQL 的官方 EX。

**关键词**：WikiSQL；WHERE 条件生成；先验知识；原子 Skill；消融实验；原能力回归

## 1 引言

WikiSQL 问句到 SQL 的转换包含选择列、聚合函数和 WHERE 条件。[1] 本研究限定在 WHERE：系统需要识别问题中的过滤信息，选择表列，判断比较方向，抽取并落地条件值，最后输出 WikiSQL 的 `conds`。原有 E4 系统既有 WHERE 失败样本，也有执行成功样本。因此只在失败集上报告改进，会忽略修改后对原本正确样本的影响。

本文回答三个问题：**RQ1**，先验知识与 Skill Flow 各自能改善哪些 WHERE 错误；**RQ2**，两者结合后的收益和模型开销如何；**RQ3**，在 E4 原本执行正确的样本上，新方案保留了多少 WHERE 能力。主实验回答前两问，独立的原能力回归回答第三问。所有差异均为固定样本上的观测结果；由于 E0 是历史预测而非同接口重新推理，本文不作因果或统计显著性宣称。

## 3 方法与实验设计

### 3.1 任务定义与指标

给定问题 \(q\) 与表 \(T\)，预测条件列表 \(C=[(c_i,o_i,v_i)]_{i=1}^k\)，其中列索引 \(c_i\) 必须属于表头范围，WikiSQL 算子编码 \(o_i\) 仅允许 `0/1/2`（分别为 `=`、`>`、`<`），\(v_i\) 为数值或文本。`>=`、`<=`、`!=` 只有可证明等价时才可转换，否则应保留不可表达状态。原始问题、表和先验上下文随 Flow 请求传递，阶段产物保存在 `stageResults`。

**表 2　评价指标与分母**

| 指标 | 判定方法 | 分母 |
| --- | --- | ---: |
| 安全完成率 SCR | `SUCCEEDED`、合法 WikiSQL `conds`；E2/E3 另要求 Flow 完成及 `WHERE_CONDITION_VALIDATE.valid=true` | 各队列全部有效样本 |
| 严格结构匹配 | 预测 `conds` 与 Gold 完全相同，保留值大小写及条件顺序 | 各队列全部有效样本 |
| 归一化结构匹配 | 文本值执行 Unicode `casefold()`；AND 条件按保留重复项的多重集比较 | 各队列全部有效样本 |
| WHERE 行一致 | 在本地 SQLite 表执行预测与 Gold 条件，比较选中的行 ID 集合 | 各队列全部有效样本 |
| 非空 WHERE 行一致 | 仅在 Gold WHERE 选中至少一行的样本上计算行一致 | 失败集 405；回归集 400 |
| 双方空结果 | Gold 与预测均选中零行，单独报告 | 不作为有效修复证据 |

评估器只比较 WHERE 过滤结果，不生成 E1–E3 的 `sel` 或 `agg`，因此**不计算这些组的完整 SQL 官方 EX**。未安全完成的样本在结构和行一致计数中均记为失败。E0/E4 冻结预测只接受其已有的 JSON/结构证据及本地 `conds` 校验；与在线 Flow 的内部验证证据不同，SCR 的绝对值应结合此差别解读。

### 3.2 两个因素与执行链路

**表 3　2×2 设计和在线入口**

| 组别 | 画布先验知识 | 原子 Skill Flow | 请求路径 |
| --- | :---: | :---: | --- |
| E0（仅主实验） | 否 | 否 | 复用冻结 E4 预测，不新增模型调用 |
| E1 | 是 | 否 | `where-prior /parse`：单次模型解析 |
| E2 | 否 | 是 | `WIKISQL_WHERE_GENERATION`，空 `knowledgeContext` |
| E3 | 是 | 是 | `WIKISQL_WHERE_GENERATION`，画布 `structure` 与 `knowledge` |

知识源于前端既有画布定义 `wikisql_where_knowledge.tsx`。运行器对每张表调用既有提取函数，将 atoms、patterns、relations 与当前表字段证据编译为知识图，保存 `knowledge_cache.json`，并在 manifest 固定缓存哈希。E1 将 `question/table/knowledge` 交给 `/parse`；E3 将 `question/table/structure/knowledge` 交给 Flow；E2 传入相同结构但空的先验集合。E1 与 E3 对知识的承载字段和额外 `structure` 并不完全一致，这是因素解释的限制。

FlowEngine 顺序调用十个已注册 Skill：`WHERE_CONDITION_EXTRACT → WHERE_MULTI_CONDITION_EXTRACT → WHERE_COMPLETENESS_CHECK → WHERE_COLUMN_MATCH → WHERE_OPERATOR_RECOGNIZE → WHERE_VALUE_EXTRACT → WHERE_SCHEMA_VALUE_MATCH → WHERE_VALUE_NORMALIZE → WHERE_CONDITION_VALIDATE → WHERE_CONDITION_ASSEMBLE`。每阶段经 `WHERE_REQUEST_MERGE` 接回统一 request，保留原问句、表、知识、条件、阶段结果与终止状态。条件提取、列匹配、算子识别、值提取调用既有模型服务；多条件边界、值落地、归一化、合法性与装配以 Java 为主，疑难条件按需复核。E2/E3 的多次模型返回反映阶段调用及必要复核，不等同于十个 Skill 每个都调用模型。

### 3.3 运行控制与可复现性

两次实验均使用模型 `gpt-5.6-sol`，并发数 2，单请求超时 600 秒，不自动重试。正式失败集运行器为 `dataset/WikiSQL_Where/experiment/run_ablation.py`；回归集适配器为 `dataset/WikiSQL_Where_return/experiment/run_regression.py`，复用前者的 HTTP 请求、验证、SQLite 比较和 Token 计数。每条原始响应单独写成 JSON；`evaluated.jsonl` 与 `metrics.json` 存放评估结果；manifest 冻结数据、抽样身份、脚本、Flow JSON、Java 实现及知识缓存的 SHA-256。指标中的缓存 Token 为模型返回的缓存输入 Token，**已包含在输入 Token 中**。

回归运行曾在 E2 #140–#145 遇到本地 Flow 端口连接拒绝，触发“五次连续传输失败”停止保护。六条无 HTTP 响应的传输失败记录保留在 `result/retention_return_20261127/recovery/transport_refused_20261127/`，本地服务重启并停用与本实验无关的 Eureka 通信后，以相同 run ID 仅重跑这些未得到模型响应的样本及剩余样本。六条均得到真实后续响应；最终统计不把原传输失败记录计为预测。Eureka DNS 错误与短时端口拒绝同时出现，但现有证据不能证明两者直接因果关系。模型调用次数仅计原始记录中可恢复的成功返回，不能视为供应商计费账单。

从 E2 到 E3，grounding 失败由 19 降至 4，SCR 由 373/400 升至 391/400；但在已具有先验的 E1 上叠加 Skill，SCR 由 393/400 小幅降至 391/400。E3 的输入 Token 约为 E2 的两倍。知识图只在本地每表构建一次，不代表模型端知识内容只传输一次；供应商返回的缓存 Token 不能直接当作节省的费用。

## 5 讨论与有效性边界

两组队列给出互补证据。失败集显示 E3 对归一化结构的增益最大，尤其体现在 W02 值落地与 W09 条件遗漏；但 E1 的 WHERE 行一致略胜 E3，说明结构更贴近 Gold 并不保证筛选行更一致。回归集显示 E3 在 E1–E3 中最能保留原能力，仍有 11 条相对冻结 E4 的 WHERE 行级损失。不能把两个定向抽样队列合并成“810 条总体准确率”：失败集与成功集按 E4 结果刻意分层，抽样比例不代表总体分布。

**主要限制**如下。

1. **评价范围**：在线臂只产生 WHERE `conds`；WHERE 行一致和官方完整 SQL EX 不是同一指标。E4 全 SQL 成功样本里仍有 1 条 WHERE 行不一致，正好说明二者不同。
2. **基线与接口不对称**：E0/E4 使用历史完整 SQL 输出；E1 用单次 `/parse`，E2/E3 用 Flow；E1 的知识字段和 E3 的 `structure + knowledge` 也不同。2×2 差分仅具描述性。
3. **Gold 与类别来源**：失败集有 12 条修订和 36 条仍标记有争议的 Gold；十四类分层来自此前汇总，缺少完整的逐样本标签文件，因此应把类别表视为探索性，不用于样本级因果归因。
4. **样本量与重复性**：各臂只运行一次，W08 等小类样本少，未给出置信区间或显著性检验。回归集虽然分层抽取，但只来自 E4 成功样本。
5. **状态与 Token 口径**：`CLARIFY`、`GROUNDING_FAILED` 和 `INVALID` 包含安全拒绝，不能一概称为模型语义错误；成功模型返回次数不是完整供应商调用账单。缓存输入 Token 包含在输入 Token 内。
6. **执行等价的局限**：WHERE 行一致只针对当前表的数据；两组都空的五条正式样本不能证明逻辑等价，回归集没有双方空结果。冗余条件即便在当前表恒真，也不能当作一般 SQL 等价。

## 6 结论

在审计后的 410 条 E4 失败样本上，E3 的归一化 WHERE 结构匹配达到 82.20%，比 E0 高 26.59 个百分点；E1 的 WHERE 行一致率 83.66% 则略高于 E3 的 83.17%。在 400 条 E4 成功样本上，E3 的归一化结构匹配为 96.50%，WHERE 行一致为 97.00%，但相对冻结 E4 的 WHERE 行一致仍净失 11 条。联合方案提升了结构质量和相对 E2 的安全完成率，代价是显著更高的输入 Token；保留既有正确结果、列语义映射、比较方向与多余条件处理仍是改进重点。现有数据支持上述固定队列上的描述性结论，尚不足以推断全 WikiSQL 测试分布的效果。
